# SDD Kit — Spec-Driven Development, portável

> **English TL;DR** — SDD Kit installs a **Spec-Driven Development** workflow into any project
> that uses Claude Code: an idea becomes a spec (**requirements → design → tasks**) and only then
> becomes verified code. The engine is generic; your project's knowledge is **generated by the
> agent from your codebase**. Gates are **by risk, not by phase** — `high` always stops for a human.
> Install with `./install.sh /path/to/project` (or `install.ps1` on Windows), then run the
> `setup-sdd` skill inside the project. No dependencies beyond Python 3.7+. Docs are in Brazilian
> Portuguese; the prompts the agent actually reads are in English.

Um kit para instalar um fluxo de **Spec-Driven Development** em qualquer projeto usando
Claude Code. Uma ideia vira uma spec (**requisitos → design → tarefas**) e só então vira código
verificado. Os portões são **por risco, não por fase**: o fluxo roda contínuo e só para em
humano no que é alto risco.

Feito para ser **copiado para o seu projeto** e adaptado em minutos — o motor é genérico;
o conhecimento do seu projeto é **gerado pelo próprio agente** a partir do seu código.

---

## O que é (modelo de 3 camadas)

| Camada | O que é | De onde vem |
|---|---|---|
| **1. Motor** | comandos SDD, rules, templates, linter | **este kit** — copie e não toque |
| **2. Projeto** | `CLAUDE.md` + `.sdd/steering/` | **gerado** por `/sdd:steering` no seu repo |
| **3. Governança** | subagentes, hooks, perfis de impl | **você decide** por projeto (opcional) |

Você não escreve o conhecimento do projeto à mão. Você copia o motor e manda o agente
ler o seu código e escrever a camada 2.

---

## Requisitos

- **Claude Code** (CLI, desktop, web ou extensão de IDE) no projeto de destino.
- **Python 3.7+** para o linter de rastreabilidade (`py` no Windows, `python3` no resto).
- Nada mais. Sem dependências, sem instalação de pacotes.

## Como obter

```bash
git clone https://github.com/fabioproven/sdd-kit-de.git
```

Ou baixe o zip da versão em **Releases** e extraia. Nos dois casos você fica com uma pasta

não precisa ficar dentro do projeto.

## Instalação em 3 passos

### 1. Copie o motor para o seu projeto

**Linux / macOS / Git Bash:**
```bash
./install.sh /caminho/do/seu-projeto
```

**Windows (PowerShell):**
```powershell
.\install.ps1 -Target C:\caminho\do\seu-projeto
```

Sem script, dá para copiar à mão: leve `.claude/`, `.sdd/settings/`, `tools/` e
`CLAUDE.md.template` para a raiz do seu projeto; crie `.sdd/steering/` e `.sdd/specs/` vazios.

### 2. Gere a camada de projeto (a parte "conversa")

Abra o Claude Code **dentro do seu projeto** e rode a skill de setup:

```
setup-sdd
```

Ela faz o bootstrap como conversa:
1. verifica o motor e detecta seu stack;
2. **intake do projeto** — pergunta, uma de cada vez: (a) **documentação técnica e convenções**
   (aponte paths/URLs ou cole — isso vem *antes* do discovery e prioriza sobre o que o glob acha);
   (b) **qual host de git** — GitHub · GitLab · Azure DevOps · Bitbucket · nenhum;
   (c) **qual tracker** — Jira · Microsoft Planner · Kanbanize · outro · nenhum;
3. **absorve conhecimento prévio** (`/sdd:absorb-knowledge`) — lê primeiro os docs que você apontou,
   depois varre `*.md` da raiz, `AGENTS.md`, `.claude/`, `.cursor/` + `.cursorrules`,
   `.github/copilot-instructions.md`, `.windsurfrules`, `.continue/`, `.aider*`, `.agent/`,
   `.assistant/` — e destila convenções, vocabulário e guardrails para o steering;
4. entrevista você para preencher o `CLAUDE.md` (uma pergunta por vez);
5. roda `/sdd:steering` para gerar `product.md` / `tech.md` / `structure.md` do seu código,
   reconciliando com o conhecimento herdado;
6. **descobre ferramentas** (`/sdd:discover-tools`) — parte do git host e do tracker que você
   declarou no intake e **verifica** se cada um é nativo (MCP/CLI) ou precisa configurar, mais a
   plataforma de dados → `integrations.md`, com passos exatos de conexão para o que falta.

> Prefere manual? Edite `CLAUDE.md`, e rode `/sdd:absorb-knowledge`, `/sdd:steering` e `/sdd:discover-tools`.

### 3. Teste ponta a ponta

```
/sdd:spec-quick "uma feature pequena e real" --spec-only
/sdd:spec-lint <feature>
```

`--spec-only` para na geração de tarefas — você inspeciona requirements → design → tasks
**sem tocar em código**. Se os três saírem coerentes e o linter passar, está instalado.

## O fluxo, do começo ao fim

```
ideia → requirements.md → design.md → tasks.md → código
        (o QUÊ)           (o COMO)     (plano)    (impl)
   ▲ aprovar req     ▲ aprovar design  ▲ aprovar tasks
```

| Comando | Faz |
|---|---|
| `/sdd:absorb-knowledge` | absorve convenções de configs de agentes prévios para o steering |
| `/sdd:discover-tools` | mapeia ferramentas disponíveis (Jira/git/dados) → `integrations.md` |
| `/sdd:steering` | (re)gera a memória do projeto a partir do código |
| `/sdd:spec-init <desc>` | cria a pasta da spec + arquivos-semente |
| `/sdd:spec-requirements <feat>` | gera requisitos testáveis (formato EARS) |
| `/sdd:spec-design <feat> [-y]` | gera arquitetura, componentes, rastreabilidade |
| `/sdd:spec-tasks <feat> [-y]` | quebra em tarefas de 1–3h com marcadores `(P)` |
| `/sdd:spec-lint <feat>` | **valida rastreabilidade** (cobertura + refs) |
| **`/sdd:spec-evals <feat> [--run]`** | golden questions + regressão — **valida correção**, não estrutura |
| `/sdd:spec-impl <feat> [task]` | implementa via TDD — **roda o loop executor↔aprovador sozinho** se `autoapprove.json` estiver ligado (0.8.0) |
| `/sdd:spec-impl-auto <feat> [task]` | alias explícito do mesmo loop |
| `/sdd:spec-quick "<desc>" [--spec-only] [--auto]` | roda tudo num comando |
| `/sdd:spec-status <feat>` | relatório de progresso |
| **`/prepare-pr [base]`** | self-review do diff + abre PR no host detectado |
| **`/review [<pr>\|--diff]`** | revisa um PR aberto ou o seu diff de trabalho |
| **`/data-quality <table> [--spec <feat>]`** | roda checks de DQ read-only na plataforma de dados |

### Perfis de implementação (escolha por tipo de trabalho)

O passo de implementação tem três variantes — use a que combina com o trabalho:

- `/sdd:spec-impl` — **código de aplicação** (TDD: teste antes do código).
- `/sdd:spec-impl-investigation` — **auditoria / root-cause** (produz um relatório de findings).
- `/sdd:spec-impl-config` — **pipeline / IaC / manifests** (validado por dry-run, não por unit test).

## O linter de rastreabilidade (o diferencial)

O ponto mais frágil de qualquer fluxo SDD é que a matriz "requisito → tarefa" é normalmente
verificada só por convenção. Aqui ela é checada de forma determinística:

```bash
py tools/spec-lint.py <feature>      # Windows
python3 tools/spec-lint.py <feature> # Linux/macOS
py tools/spec-lint.py --all          # todas as specs
```

Ele falha (exit 1) se:
- algum ID de requisito **não tem tarefa** (cobertura),
- alguma tarefa cita um ID de requisito que **não existe** (referência solta),
- e avisa sobre sub-tarefas sem linha `_Requirements:_`.

Wire no CI como check obrigatório de qualquer mudança de spec.

**No editor (novo em 0.7.0).** `--format=vscode` troca o relatório por uma linha ancorada por achado:

```
.sdd/specs/minha-feature/requirements.md:21:1: error: Req 2.2 não é referenciado por nenhuma tarefa (cobertura)
.sdd/specs/minha-feature/tasks.md:12:1: error: referência solta: Req 9.1 não existe em requirements.md
```

É o que o `.vscode/tasks.json` instalado pelo kit consome: **Ctrl+Shift+B** roda o lint de todas as
specs e cada achado vira item clicável no painel **Problems**, que abre o arquivo na linha exata. A
trava sai da conversa e vai para onde o dev já olha — guardrail determinístico, não instrução no
prompt. O formato `human` continua sendo o default.

## Semântica, evals e proveniência (novo em 0.6.0)

O linter garante que a spec é **rastreável**. Ele não diz nada sobre a resposta estar **certa** —
esse é o outro eixo, e é onde agente de dados falha silenciosamente. Três peças, todas opcionais e
inertes em projeto sem plataforma de dados:

- **Semantic layer** (`/sdd:steering-custom` → `semantic-layer.md`): contrato por métrica —
  nome + fórmula + **grain** + população + fonte + dono. `SUM(valor)` não é métrica; `receita_liquida`
  é. Métrica sem contrato **não se inventa**: propõe, confirma, escreve no steering, aí usa.
- **Escada de fontes** (`rules/data-readiness.md`): semantic layer → modelo governado → SQL manual →
  raw. Descer de degrau é permitido; descer **em silêncio** não é. Fonte ambígua é finding.
- **Evals** (`/sdd:spec-evals`): 10–20 golden questions com **ground truth humano** — incluindo uma
  pergunta ambígua cuja resposta certa é *pedir esclarecimento* e um caso de borda. Ground truth
  gerado pelo próprio agente mede consistência, não correção. `--run` executa read-only e reporta
  PASS/FAIL/SKIPPED; eval sem ground truth é **SKIPPED, nunca PASS**.

O `spec-lint` incorpora a checagem de forma aditiva: se `evals.md` existe, ref morta é erro e
requisito sem eval é aviso; `py tools/spec-lint.py <feat> --require-evals` promove tudo a erro e
exige a suite (para CI de projeto que já escreve evals). Sem `evals.md` e sem a flag, o
comportamento é idêntico ao da 0.5.0.

E toda resposta com número sai com **proveniência** (`rules/answer-provenance.md`): fonte, métrica,
freshness, validação, confiança — com a premissa nomeada quando a confiança é baixa.

## Conhecimento herdado & descoberta de ferramentas (novo em 0.2.0)

O setup não parte do zero e não adivinha o ambiente:

- **`/sdd:absorb-knowledge`** varre configs de agentes prévios (Cursor, Copilot, Claude, Gemini,
  Aider, Windsurf) e docs da raiz, e destila convenções, vocabulário e guardrails para
  `.sdd/steering/inherited-knowledge.md` — reaproveitando o que o time já escreveu. Distila, não
  copia; sinaliza conflitos entre fontes; nunca carrega segredos.
- **`/sdd:discover-tools`** sonda (read-only) quais backends o projeto realmente dirige — issue
  tracker (Jira/Linear/…), VCS & PR host (GitHub/GitLab/Azure DevOps), plataforma de dados
  (Databricks/BigQuery/Snowflake) e CI — e classifica cada um como `mcp-native`, `cli`,
  `needs-setup` ou `n/a` em `.sdd/steering/integrations.md`, com uma lista **"To enable"** do que
  falta configurar.

Os comandos de entrega **leem `integrations.md`** antes de agir: `/prepare-pr` e `/review` usam a
linha VCS/PR; `/data-quality` usa a linha de dados. Se a linha necessária for `needs-setup`, o
comando **para** e diz o que configurar — nunca chuta uma ferramenta errada.

## Modo aprovador automático (novo em 0.4.0, desligado por padrão)

Reduz aprovações manuais com um padrão orquestrador de **dois papéis**: um agente **executor**
(planeja e aplica, comportamento de hoje) e um agente **aprovador** separado, com prompt próprio e
**sem acesso de escrita**, que avalia o resultado contra critérios de saída objetivos e decide
**APPROVE / REJECT (com feedback) / ESCALATE**.

**Classificação de risco** (antes de executar cada subtarefa):

| Nível | Quem aprova | Exemplos |
|---|---|---|
| **low** | automático | ler pastas, analisar estrutura, gerar documentação, queries read-only |
| **medium** | aprovador automático decide, tudo logado | novo modelo/tabela, nova transformação, testes |
| **high** | **sempre humano, sem exceção** | mudança de schema, delete/overwrite, migração, push/deploy |

**Guardrails contra loop infinito — determinísticos, fora do modelo** (`tools/approval-gate.py`):

- **Máximo de iterações por subtarefa** (default 5): o gate conta os vereditos no ledger e, no teto,
  **escala para o humano**. Loop infinito é impossível por construção — não depende do modelo contar certo.
- **Teto de tokens/custo por subtarefa**: ao cruzar, escala.
- **Critério de saída explícito e verificável** por ciclo — nada de aprovação subjetiva; o que não é
  pass/fail escala.
- **high / master desligado / nível não habilitado** → o gate retorna `HUMAN`; o loop nem começa.

**Observabilidade**: cada decisão vai para `.sdd/specs/<feature>/approval-log.jsonl` (quem decidiu,
iteração, risco, tokens, custo). `py tools/approval-gate.py summary --feature <f>` consolida.

**Configurável e reversível**: `.sdd/autoapprove.json` liga/desliga por nível de risco.
`enabled: false` (default) = **comportamento idêntico ao manual** — o modo automático é estritamente
aditivo, o fluxo de aprovação atual continua sendo o fallback.

**Como é acionado (mudou na 0.8.0).** Com `enabled: true`, **todo `/sdd:spec-impl*` roda o loop
sozinho** — `spec-impl`, `spec-impl-config`, `spec-impl-investigation` e, por tabela, `spec-quick`.
Não há comando separado para lembrar; `/sdd:spec-impl-auto` continua existindo como alias explícito.
A lição veio do uso real: o loop ficou cinco meses ligado na config e nunca rodou, porque vivia num
comando paralelo ao que a pessoa já chamava. A prova de que rodou é o `approval-log.jsonl` na spec —
o `spec-status` avisa quando uma spec tem tarefa marcada e não tem ledger.

```
/sdd:spec-impl <feature> [tarefas]      # loop automático se autoapprove.json estiver ligado
```

## Em produção: o que cinco meses de uso provaram (0.8.0)

Um projeto real de plataforma de dados (People Analytics, ~2.400 notebooks) rodou o motor por cinco
meses. O inventário, em números anonimizados:

| Medida | Resultado |
|---|---|
| Specs criadas pelo fluxo | **35** (de 4 a 9 requisitos cada) |
| IDs de requisito rastreados | **~1.000** |
| `spec-lint --all` | **35/35 passam**, 0 erros |
| Camada 2 gerada (`steering`, `inherited-knowledge`, `integrations`) | sobreviveu ao uso sem regeneração |
| Loop executor↔aprovador (ligado na config) | **0 execuções** — vivia num comando que ninguém chamava |
| Grafias distintas de "implementado" em `spec.json` | 11 |
| Artefatos que o template não previa | 13 (`impacto-contrato`, `evidencia-*`, `rollback/`…) |

As três últimas linhas são a 0.8.0. A rastreabilidade — o diferencial — aguentou; o que falhou
foi tudo que dependia de a pessoa **lembrar** de um comando ou de um nome. Daí a regra desta
versão: comportamento novo entra no comando que já se usa, e o que o uso inventa ganha nome fixo.

## Os agentes de dados e a trava de escrita (0.8.0)

Para projeto com plataforma de dados — sem ela, nada disto é acionado.

- **`data-analyst`** (`.claude/agents/`) — toda consulta cara passa por ele e o contexto principal
  recebe só a conclusão: só leitura por construção; **escada de amostragem** (metadados → agregação →
  amostra `LIMIT 50` → escalona pedindo autorização); PII proibida; número sempre com proveniência;
  **nunca dump**. Conecta pelo que `integrations.md` diz — perfil, warehouse, armadilhas de CLI —
  nunca por padrão implícito.
- **`report-validator`** — auditor adversarial de qualquer relatório (HTML, Markdown, notebook, PDF
  exportado) **antes de circular**. Reproduz cada número na fonte e rotula: `CONFIRMED`,
  `CONTRADICTED`, `NOT REPRODUCIBLE`, **`LABEL TOO BROAD`** (conta certa, conjunto nomeado maior que
  o medido), **`MIXED AXES`** (colunas que respondem perguntas diferentes lado a lado), `UNSUPPORTED`,
  `POSSIBLY STALE` (a tabela materializou versão nova depois da medição). Julga; não edita.
- **`tools/write-guard.py`** — hook `PreToolUse` que **nega** escrita SQL fora de
  `.sdd/write-scope.json` e pede confirmação em alvo ambíguo. Instala **desligado**. Antes de ligar:
  ```bash
  py tools/write-guard.py --self-test            # padrões + o que a sua config libera/nega
  py tools/write-guard.py --check "MERGE INTO prod.core.t USING s ON 1=1"
  ```
  e confirme **na plataforma** que cada schema permitido existe com a grafia exata — a instalação
  que inspirou a tool passou um mês com o schema grafado errado, negando o alvo certo e liberando um
  inexistente. O hook só vale onde hook roda: dentro de um notebook hospedado ele não existe, e o
  `CLAUDE.md.template` agora tem a tabela "Where you are running" para dizer isso ao agente.

## Artefatos com nome fixo, fase canônica e entrega sem repositório (0.8.0)

`rules/spec-artifacts.md` dá nome ao que o uso inventou, para que `spec-status` e `spec-lint`
enxerguem:

| Artefato | Papel | Quem lê |
|---|---|---|
| `contract-impact.md` | quais consumidores (dashboards, APIs, outros pipelines) dependem do que a spec muda | `risk-classification`: tarefa que toca contrato listado é **`high`** |
| `evidence/<o-quê>-<AAAA-MM-DD>.md` | prova datada de que um passo rodou, com proveniência | `spec-status`, `report-validator` |
| `rollback.md` | como desfazer — obrigatório antes de `high` que sobrescreve | o humano no portão |

`spec.json.phase` passa a ter **sete valores canônicos** (`initialized` … `implementation-complete`);
nuance vai em `status_note`. O `spec-lint` avisa fase desconhecida, inclusive no painel Problems.

E quando **não há git por decisão** — o workspace da plataforma é o versionamento — a linha VCS de
`integrations.md` aceita `platform`, e `/prepare-pr` monta um **pacote de entrega** em vez de PR:
frescor do remoto conferido, lista exata do que mudou, um comando de import por arquivo, rollback,
e "sim" explícito antes de cada import. Sempre `high`.

## Três invariantes a proteger (não quebre isto ao adaptar)

1. **Separação QUÊ / COMO** — `requirements.md` descreve comportamento testável, **sem** nomes
   de arquivo ou classe. `design.md` é onde a solução técnica vive.
2. **Rastreabilidade** — o mesmo ID (`Req 2.1`) viaja de requisitos → design → tarefa → checkbox.
   O linter existe para garantir isso.
3. **Portões por risco, não por fase** — `low` e `medium` correm sozinhos e logados quando o modo
   aprovador está ligado (a postura que o `setup-sdd` recomenda); **`high` é sempre humano, sem
   exceção** — schema, delete/overwrite, migração, credencial, qualquer coisa irreversível.
   Nenhuma flag ou config auto-aprova `high`. Com o modo desligado, todo portão é humano.

│   ├── settings/kit-history.json   caminhos que cada versão publicou (colisão por nome no upgrade)

do seu projeto. Tudo que é específico nasce em `CLAUDE.md` e `.sdd/steering/`.

## Versionamento

O motor é versionado (`VERSION`). Ao trazer uma versão nova do kit, reinstale a camada 1 —
o seu `.sdd/steering/` e as suas specs **não são tocados**. Para realinhar o steering ao código
depois de mudanças grandes, rode `/sdd:steering` (modo Sync: aditivo, preserva o que você escreveu).

**Atualizar sem perder contexto (0.7.0).** Reinstalar deixou de ser escrita cega. Antes de copiar, o
instalador tira backup de tudo que pode tocar (`.sdd/backups/pre-<versão>-<timestamp>/`); depois,
compara o que estava lá com o manifesto da instalação anterior (`.sdd/.kit-manifest.json`, sha256 por
arquivo):

| Situação | O que acontece |
|---|---|
| Arquivo de motor igual ao manifesto | recebe a versão nova, em silêncio |
| Arquivo de motor **editado no destino** | sua edição é restaurada; a do kit fica como `<arquivo>.sdd-new` |
| Arquivo que sumiu do motor novo | é listado no relatório, **nunca apagado** (remoção é decisão humana) |
| `steering/`, `specs/`, `CLAUDE.md` | fora do alcance do instalador, como sempre |

O resultado vai para `.sdd/UPGRADE.md`: de onde veio, o que foi preservado, o que revisar e **o que a
camada 2 ainda deve à versão instalada** — steering ausente, `CLAUDE.md` ainda com `{{PLACEHOLDERS}}`
ou ainda descrevendo portão por fase, spec sem `evals.md` —, cada item com o comando que o gera.
Leia esse arquivo antes de qualquer outra coisa depois de atualizar.

Sem Python 3 no PATH, o instalador avisa e se comporta como na 0.6.0 (sem backup, sem manifesto).

*SDD Kit 0.8.0 — adapte à vontade. Comece pelo `setup-sdd`.*

### Novidades da 0.8.0
- **O loop auto roda dentro do `spec-impl`** — ligado em `autoapprove.json`, todo `/sdd:spec-impl*` (e o
  `spec-quick`) executa o loop executor↔aprovador sozinho; `spec-impl-auto` vira alias. Cinco meses
  de uso real com o loop ligado e zero execuções ensinaram: comando paralelo não existe na prática.
- **`data-analyst` e `report-validator`** — subagentes de dados: consulta só leitura com escada de
  amostragem e sem dump; auditoria adversarial de relatório antes de circular (`LABEL TOO BROAD`,
  `MIXED AXES`, `POSSIBLY STALE`).
- **`tools/write-guard.py`** — hook determinístico que nega escrita SQL fora de `.sdd/write-scope.json`;
  instala desligado; `--self-test` e `--check` para provar o que ele nega antes de confiar.
- **`rules/spec-artifacts.md`** — fase canônica (7 valores, aviso no lint) e nome fixo para
  `contract-impact.md` (⇒ `high`), `evidence/` e `rollback.md`.
- **Entrega sem repositório** — linha VCS `platform` em `integrations.md`; `/prepare-pr` monta pacote
  de import seletivo, sempre `high`.
- **`kit-sync` reconhece colisão por nome** (`kit-history.json`): arquivo que o kit passa a publicar mas
  o projeto já tinha, e nenhuma versão publicou, é preservado — kit ao lado como `.sdd-new`.
- `CLAUDE.md.template` com "Where you are running" (hook não existe dentro do workspace hospedado) e
  roteamento para os agentes de dados; `settings.local.json` semeado com a lista `ask` de destrutivos.

### Novidades da 0.7.0
- **O linter fala com o editor** — `spec-lint --format=vscode` emite `arquivo:linha:coluna` por achado,
  e o `.vscode/tasks.json` instalado pelo kit joga tudo no painel **Problems** (Ctrl+Shift+B).
- **`.vscode/` faz parte da instalação** — tasks, settings (specs agrupadas no explorador) e
  recomendação da extensão do Claude Code. Nunca sobrescreve o que o projeto já tem.
- **Upgrade com memória** (`tools/kit-sync.py`) — backup antes de copiar, edição local preservada por
  hash, sobras da versão antiga listadas em vez de apagadas.
- **`.sdd/UPGRADE.md`** — relatório por instalação, incluindo o que a camada 2 ainda deve ao motor.

### Novidades da 0.6.0
- **Semantic layer como steering** — contrato por métrica (fórmula, grain, população, dono),
  entidades canônicas e os termos que o negócio usa de forma ambígua.
- **Escada de fontes + checklist Agent-Ready** (`rules/data-readiness.md`) — e a regra de que descer
  de degrau em silêncio é proibido; grain ou dono ausente é bloqueio.
- **`/sdd:spec-evals`** — golden questions com ground truth humano, validação adversarial por revisor
  separado, e regressão. `spec-lint` ganha a checagem (aditiva) + flag `--require-evals`.
- **Proveniência obrigatória** — todo número sai com fonte, métrica, freshness, validação, confiança.
- **Canvas de caso de uso no `setup-sdd`** — ações permitidas e nível de autonomia declarados no
  bootstrap, alimentando o escopo de risco `high`.

### Novidades da 0.5.0
- **Autonomia por padrão — portões por risco, não por fase.** O `CLAUDE.md` gerado roda
  spec→design→tasks→impl contínuo e só para em humano no `high` (escrita em dado produtivo, mudança de
  schema, contrato de consumidor, deploy/PR). `low`/`medium` rodam sem pedir aprovação.
- **`setup-sdd` recomenda a postura Equilibrada** (auto `low`+`medium` logado, `high` sempre humano) e
  **semeia uma allowlist read-only** em `.claude/settings.local.json` — nunca comando de escrita.
- `max_iterations` padrão 3 → 5. Template `autoapprove.json` continua `enabled:false` (opt-in guiado).

### Novidades da 0.4.0
- **Modo aprovador automático** — padrão orquestrador executor↔aprovador, com classificação de risco
  (low/medium/high), trava determinística contra loop infinito (`tools/approval-gate.py`, cap de
  iterações + teto de custo), log de todas as decisões, e configurável por nível em `.sdd/autoapprove.json`.
  Desligado por padrão: o comportamento manual atual continua sendo o fallback.
- Novos: comando `/sdd:spec-impl-auto`, agente `approver` (sem escrita), rules `risk-classification`
  e `orchestration-loop`.

### Novidades da 0.3.0
- **Intake no setup** — o `setup-sdd` agora *solicita*, uma de cada vez: documentação/convenções do
  projeto (antes do discovery), qual host de git (GitHub/GitLab/Azure DevOps/Bitbucket/nenhum) e qual
  tracker (Jira/Microsoft Planner/Kanbanize/outro/nenhum).
- `discover-tools` parte dessa intenção declarada e **verifica**; novos backends (Bitbucket, Planner,
  Kanbanize) + tabela de conexão com passos exatos para cada `needs-setup`.

### Novidades da 0.2.0
- `/sdd:absorb-knowledge` — reaproveita conhecimento de agentes/IA prévios no steering.
- `/sdd:discover-tools` — mapeia integrações (Jira/git/dados) e o que precisa de MCP → `integrations.md`.
- Comandos de entrega bem definidos: `/prepare-pr`, `/review`, `/data-quality` — todos cientes das integrações.
- `setup-sdd` agora orquestra as descobertas antes de gerar o steering.

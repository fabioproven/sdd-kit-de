# Evaluation Rules

"It looks right" is not verification. Loaded by `/sdd:spec-evals`, and by the `/sdd:spec-impl*`
profiles when the spec carries an eval suite (`.sdd/specs/<feature>/evals.md`).

The kit already validates **structure** deterministically (`spec-lint.py` for traceability,
`approval-gate.py` for the loop). Evals close the remaining gap: whether the thing is *correct*.

## Two kinds of eval

| Kind | Question it answers | Typical project |
|---|---|---|
| **Answer eval** | Given a real business question, does the agent return the right number, from the sanctioned source? | analytics / read agents |
| **Artifact eval** | Does the thing we built behave as specified — schema, row counts, dry-run clean, idempotent re-run? | pipeline / engineering work |

Artifact evals are the `/data-quality` assertions promoted to a **regression suite** that outlives
the spec. Answer evals are golden questions with ground truth.

## The offline loop

```
golden question -> agent -> query -> result -> compare to ground truth -> PASS / FAIL
```

**Ground truth never comes from the agent under test.** It comes from a human, an existing trusted
report, or an independently computed number. A suite whose answers the agent authored measures
consistency, not correctness.

## Adversarial validation (a second, separate pass)

For high-stakes answers, a **separate reviewer** checks the reasoning rather than the prose:

- Right source (which rung of the ladder)? · Right grain? · Right population filter?
- Right join (no fan-out)? · Right denominator? · Right period/timezone?
- Is the magnitude plausible against a known reference?

It buys accuracy at a real cost in tokens and latency — reserve it for metrics that drive decisions.
This is the same pattern as the `approver` agent (`.claude/agents/approver.md`), applied to answers
instead of subtasks: **the agent that did the work never grades its own work.**

## Regression discipline

- Every bug that reaches a user becomes a golden question in the suite.
- The suite re-runs whenever the **semantic layer**, a **canonical dataset**, or the **agent's
  instructions** for that domain change. Those three are the things that silently break answers.
- A failing eval blocks the same gate that a failing test blocks — it is not advisory.

## Sizing and when it is required

Start at **10–20 questions** covering the domain's real questions, including:
- the two or three questions people actually ask weekly,
- one question whose correct behavior is **to ask for clarification** (ambiguity is not failure),
- one question at a boundary (empty period, new entity, late-arriving data).

An eval suite is **required** when the feature changes a metric definition, a canonical dataset, or
the agent's domain instructions. It is optional for local, non-data work.

## Anti-patterns

- Ground truth generated by the agent being evaluated.
- Asserting prose wording instead of the number, the source, and the grain.
- A suite of only happy-path questions — it will pass forever and catch nothing.
- Treating a passing suite as proof of correctness beyond what it covers. Say what it covers.
